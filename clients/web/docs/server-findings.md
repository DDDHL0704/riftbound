# 网页对战前端开发中发现的服务端问题

记录日期：2026-10-23。整理人：网页对战前端（`clients/web`）开发会话。

> **2026-11-01 更新**：S1–S8 已由 BACKLOG P1-2、P1-3、P1-4 在服务端解决。前端已删除逐张询价、先横置再打出、先回收再布置待命这些绕行方式，改为在同一条命令里携带 `TAP_RUNE:` 和 `RECYCLE_RUNE:`。下文保留当时的记录，行号和"前端处理"不再代表现状。

> **2026-11-01 新增 S9（低）**：单位技能"回收一张废牌"的费用必须且只能选一个（`RecycleMightRules.cs`），但提示里没有 `requiredOptionalCostChoiceCount`。前端目前按 `RECYCLE_GRAVEYARD_CARD:` 前缀识别，建议服务端补上这个标记。

本文汇总 2026-10-22 至 10-23 各轮网页前端开发和自动对战回归中，服务端行为影响前端功能的地方。每一条都对照了服务端源码，并按官方中文规则或 FAQ 核对过规则依据。本文只记录现象、证据和建议，**没有修改任何服务端代码**。

- 服务端代码以 `origin/main` 提交 `489c3fe7` 为准（这也是自动对战回归所用的版本）。文中的行号都指这个提交。
- 规则条款编号来自 2026-10-10 更新的《符文战场：英雄联盟对战卡牌》核心规则（中国区，zh-CN），来源见文末。
- 本文不是规则认证。项目仍处于 Goal active / NOT READY 状态，这里只覆盖网页前端实际碰到的范围。

### S1　出牌候选只看法力池里已有的法力（高）

**现象**

在对手回合里，手上的伏击牌、反应牌明明可以靠横置自己的符文付费，界面上却没有打出选项。这就是试玩时反馈的"伏击牌打不出来"。只有先手动横置符文、让法力进入法力池之后，服务端才会给出这张牌的 `PLAY_CARD` 候选。

**服务端证据**

- `src/Riftbound.Engine/MatchSession.cs:12592`：出牌候选用 `PromptAvailableManaWithLuxSpellOnlyResource(...) >= PromptMinimumManaCost(...)` 过滤。
- `src/Riftbound.Engine/MatchSession.cs:14587`：可用法力 = `runePool.Mana` 加上拉克丝"仅法术"资源。没有计入可以横置的活跃符文。
- `src/Riftbound.Contracts/Protocol.cs:190`（`PlayCardCommand`）：命令里只能通过 `OptionalCosts` 携带"回收符文"的付费动作，不能携带"横置符文"的付费动作。法力必须在提交前就已经在池里。

**规则依据**

- 164.2.a：基础符文拥有"[反应][>] [E]：获得[1]"。
- 204.4.b.1：带"获得资源"且拥有[反应]的主动技能，可在任何需要支付费用的时机激活。
- 430.3：带"获得资源"且拥有[反应]标签的主动技能，可以在法术与技能需要支付资源的任何时间激活。举例写明，启动"打出法术"的过程后，玩家也可以在"支付费用"步骤激活这类效果，获得法力或符能并支付费用。
- 430.2.a：确认或结算"获得"技能不会传递优先行动权或焦点。
- 166.2：法力和符能必须先加入符文池才能消耗。所以"先横置、再支付"本身不违规，问题在于服务端没有把"可以横置后付得起"的牌列为可打出。

**对前端的影响**

玩家不知道这张牌其实能打，必须先猜"要不要先横置符文"。

**前端目前的绕行方式**（`489c3fe7`）

- 每个提示到达时，对没有出现在候选里的手牌和英雄牌调用 `PreviewPlayCard` 询价，得出还差多少法力。差额不超过可横置符文数的，标成"可自动付费"。
- 点击或拖出这类牌时，先提交一次批量 `TAP_RUNE`，再按新提示里的候选打出。
- 对需要目标的牌无法准确询价（见 S4），只能按牌面费用估算。偶尔会出现"已横置符文，但这张牌仍不能打出"。这时横置得到的法力会留到下一次清空（167：每名玩家主阶段开始时和回合结束时清空）。

**建议**

- 候选计算时，把"可横置的活跃符文"和其他带[反应]的获得资源技能计入可用法力。
- `PLAY_CARD` 允许像回收符文一样携带"横置符文"的付费动作，在同一条命令里完成横置和支付。
- 至少在候选上给出"需要先横置 N 枚符文"之类的标记，让客户端不必逐张询价。

### S2　待命布置要求法力池里已有符能（中）

**现象**

手里有待命牌、也有可回收的符文，但法力池里没有符能时，服务端不给出 `HIDE_CARD` 的标准费用选项。玩家必须先单独回收一枚符文，才能布置。

**服务端证据**

- `src/Riftbound.Engine/MatchSession.cs:9824`：`if (pool.TotalPower >= 1) choices.Add(new(StandbyHideOptionalCost, ...))`。
- `src/Riftbound.Engine/CoreRuleEngine.Standby.cs:106` 起：标准待命布置扣 1 点任意符能，直接从当前法力池扣，命令里不能附带回收动作。

**规则依据**

- 811.1.b：待命的费用是支付[A]（1 点任意特性的符能），从下回合开始此牌获得[反应]，可以无视基础费用打出。服务端扣费数额与此一致。
- 204.4.b.1、430.3：同 S1，支付费用时可以激活[反应]获得资源技能。基础符文的"回收此牌：获得[C]"（164.2.b）属于此类。

**建议**

候选判断计入可回收的符文，并允许 `HIDE_CARD` 携带回收付费动作，和 `PLAY_CARD` 的回收付费保持一致。

**未核实的部分**

传奇技能（`LEGEND_ACT`）、主动技能（`ACTIVATE_ABILITY`）的候选可能也有同样的"只看池中资源"问题，这次没有逐一核实。

### S3　出牌时多回收的符文会被拒绝（中，待规则确认）

**现象**

出牌时如果勾选的回收符文超过所需符能，整条命令会被拒绝，原文是英文："Payment resource actions are not required to play 提莫."。

**服务端证据**

- `src/Riftbound.Engine/CoreRuleEngine.cs:19022-19034` 调用 `AreRecycleRunePaymentResourceActionsRequired`。
- 该函数定义在 `src/Riftbound.Engine/CoreRuleEngine.cs:10919`，判定规则有两条：
  - 当前法力池已够付，却附带了回收，就拒绝；
  - 去掉任意一枚回收仍够付，也拒绝。

**规则核对**

在 164.2.b（回收此牌：获得[C]）、203-205（费用）、417（回收）、430（获得）中，没有找到"支付时获得的资源不得超过所需"的限制。430.4.a 只要求"仅可在游戏效果的指示下获得资源"，符文自身的技能就是这样的指示。另外，玩家在出牌命令之外单独提交 `RECYCLE_RUNE` 不受这个限制，多出的符能会留在法力池里，直到下一次清空（167）。

**结论**

这更像是服务端为了"最小支付"做的设计取舍，不是规则要求。请服务端或规则负责人确认：要么放开，要么在规则依据里写明来源。

**前端处理**

前端只在确实缺符能时才显示回收选项，并限制最多勾到刚好补足。

### S4　费用询价接口要求命令完整（中）

**现象**

需要目标的牌，在玩家选目标之前无法询价。因此无法提前知道这张牌缺多少费用，"可自动付费"只能估算。选完目标后如果询价失败，只能显示统一文案"当前选择无法打出，请检查目标、位置和支付资源。"，玩家看不出具体原因。

**服务端证据**

`src/Riftbound.Engine/CoreRuleEngine.PlayCostPreview.cs:20-24`：`TryBuildPlayCardPlan` 失败时，返回固定的统一文案，并丢弃 `rejection` 里的具体原因，只保留错误码。缺少必选目标时就是这条路径。

**相关现象**

目标带法盾时要额外支付符能，例如回归中出现过的 "Not enough power to play 烟幕弹."。这类附加费用只有选定目标后询价才知道，我使用到的提示字段里没有逐个目标的附加费用。

**建议**

- 允许不带目标询价，返回基础费用和已知的增减费，目标相关的附加费用单独标注为"取决于目标"。
- 询价失败时，返回 `rejection` 的具体原因。

### S5　支付窗口不能在支付过程中横置符文（低）

**现象**

触发技能或额外费用的支付窗口里选"支付"时，如果法力池不够，会被拒绝："资源不足，可以先使用符文或反应资源技能。"。需要先单独提交 `TAP_RUNE`，等新提示到达后再支付。

**服务端证据**

- `src/Riftbound.Engine/CoreRuleEngine.Tempered.cs:251`
- `src/Riftbound.Engine/CoreRuleEngine.TriggerCosts.cs:224`

**规则依据**

同 S1：204.4.b.1、430.3。

**前端处理**

支付面板在法力不够时提供"横置 N 枚符文并支付"：先横置，拿到新的支付窗口后再支付。这样能用，但要两次往返，中间如果局面变化还可能失败。

**建议**

`PAY_COST` 的 `paymentChoiceIds` 允许携带横置符文，和回收符文一样处理。

### S6　部分拒绝原因是英文（低）

服务端多数拒绝原因是中文，下面几条是英文，前端只能按错误码显示中文说明：

- `src/Riftbound.Engine/CoreRuleEngine.cs:19014`："Invalid printed power allocation."
- `src/Riftbound.Engine/CoreRuleEngine.cs:19031`："Payment resource actions are not required to play {牌名}."
- `src/Riftbound.Engine/CoreRuleEngine.cs:19144-19148`："Not enough mana / power / experience / resources to play {牌名}."

### S7　待命布置费用选项缺少"单选"标记（低）

**现象**

`HIDE_CARD` 的费用选项通过 `optionalCosts` 下发，字面上看是"可选、可多选"。实际上服务端要求正好选一个。

**服务端证据**

`src/Riftbound.Engine/CoreRuleEngine.Standby.cs:83-86`：`costs.Count != 1` 时拒绝，提示"{牌名} 不能以该费用进行待命埋伏。"，错误码却是 `UNSUPPORTED_CARD_BEHAVIOR`，看起来像"这张牌不支持"。

**前端处理**

前端对 `HIDE_CARD` 做了特殊处理，改成单选步骤。

**建议**

在提示元数据里标明必选数量，错误码改为 `INVALID_TARGET` 或 `INVALID_PAYLOAD`。

### S8　未提供的命令返回阶段错误（低）

**现象**

客户端用当前提示的 ID 提交了一个当前提示里并没有提供的操作，服务端不会按"此操作当前未提供"拒绝，而是进入该操作自己的规则检查，返回阶段错误。

**例子**

回归中，客户端在对手回合（当前提示只有"等待 / 认输"）提交了移动单位，得到"移动单位只能在当前玩家的开放主阶段提交。"（`src/Riftbound.Engine/CoreRuleEngine.cs:11320`）。

**说明**

规则合法性仍由服务端判定，没有安全问题。但客户端很难区分"我选错了"和"我的选择已经过期"。这次触发它的是前端自己的问题，见第三节 R1。

**建议**

如果命令类型不在提示的已启用候选里，统一返回 `PROMPT_EXPIRED` 或专门的错误码。

## 二、核对后确认服务端正确的地方

下面这些在试玩或开发中曾被怀疑是服务端问题，核对规则后确认服务端行为正确：前端已经按规则调整，或者需要向玩家解释。

| 编号 | 怀疑点 | 结论 | 规则依据 |
| --- | --- | --- | --- |
| V1 | "未横置的符文不应能回收" | 服务端允许回收活跃符文，是对的。基础符文的回收技能费用只有"回收此牌"，不需要先横置。前端只把"横置并回收"排在前面，并给"仅回收（损失法力）"加了提醒 | 164.2.b |
| V2 | 声明战斗时不能挑选参战单位 | 是对的。战场进入争夺后，进攻方和防守方在该战场上的所有单位都获得进攻方或防守方身份 | 466.2.c.3 |
| V3 | "待命牌无法翻开" | 待命牌从下回合开始才获得[反应]、才能打出。布置当回合不能翻开是规则要求。试玩中看不到待命牌是前端没有渲染，已修复 | 811.1.b |
| V4 | 待命布置费用 | 服务端扣 1 点任意特性符能，与规则一致；提莫替换为 1 点法力 | 811.1.b、`CoreRuleEngine.Standby.cs:106` |
| V5 | 横置得到的法力会不会立刻丢失 | 不会。法力池在每名玩家主阶段开始时和回合结束时清空，中途不清空 | 167 |
| V6 | 对手一行动，我方提示就失效 | 这是服务端权威的设计：对手行动后旧提示过期（`PROMPT_EXPIRED`）。前端不自动重试，提示玩家按新局面重新操作 | 不涉及规则 |
| V7 | 伏击牌的打出位置 | 服务端允许把伏击牌打出到有己方单位的战场，没有问题。问题只在 S1 的费用判断 | 822.1.b |

## 四、尚未覆盖的范围

- **效果伤害分配**（`ASSIGN_EFFECT_DAMAGE`，例如沃利贝尔、阿尔法突袭）：所有预组卡组里都没有能触发它的牌，服务端也没有对应的测试场景。前端面板是按服务端校验规则写的，没有在真实对局中跑过，所以这里没有服务端结论。
- **进攻触发目标**（例如冰谷弓箭手）：回归中没有作为进攻方参战，没有实测。
- 传奇技能、主动技能的候选是否也有 S1 那样的问题：没有逐一核实（见 S2 末尾）。
- 英文版官方规则中心（playriftbound.com）本次没有重新获取；本文只依据中国区中文规则和 FAQ。
