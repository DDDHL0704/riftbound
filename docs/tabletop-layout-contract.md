# Tabletop Layout Contract

更新时间：2026-06-18

对战桌面目标是还原 Tabletop Simulator / 桌垫的空间关系，同时保持服务端规则权威。布局可以像 TTS，但每个区域的含义、可见性和交互都必须符合官方规则与当前协议。

## 坐标数据源

桌面坐标统一存放在：

`src/Riftbound.DevUi/src/components/match/tabletopLayoutData.json`

坐标采用百分比：

- `x` / `y`：区域左上角相对玩家半场或中央战场容器的位置。
- `width` / `height`：区域宽高。
- 所有区域必须落在 `0..100` 的容器范围内。

检查命令：

`npm --prefix src/Riftbound.DevUi run check:tabletop-layout`

## 玩家半场必备区域

每名玩家必须拥有这些区域：

| 区域 | 规则含义 | 前端约束 |
|---|---|---|
| `legend` | 传奇区 | 只能渲染服务端快照公开的传奇对象。 |
| `champion` | 英雄区 | 只能渲染服务端快照公开的英雄对象。 |
| `score` | 分数/牌堆状态 | 展示服务端分数、主牌剩余、符文剩余，不自行结算得分。 |
| `piles` | 主牌、废牌、放逐、战场池等牌堆入口 | 对公开牌堆只显示可公开的顶牌或数量；不泄漏牌堆顺序。 |
| `base` | 基地区 | 展示基地及服务端允许公开的基地对象；符文牌不混放在基地单位/对象层。 |
| `runeBank` | 符文堆与已召出符文槽 | 固定 12 张符文容量；只显示服务端公开的符文对象。 |
| `hand` | 手牌 | 本方可见，对手只显示数量/卡背，不泄漏卡名。 |

## 符文槽规则

- 符文牌堆固定为 12 张。
- 回合开始流程由服务端执行；前端只读 `runeDeckCount`、`runePool` 和公开符文对象。
- 已召出的符文在 `runeBank` 横向槽中显示，最多 12 个槽。
- 未公开符文不能通过前端占位、tooltip、alt 文本或日志泄漏身份。

## 中央战场

- 当前 1v1 桌面固定显示两处公共战场。
- 战场卡、控制者、争夺状态、待命、参战单位、本回合得分和 pending task 都来自服务端 snapshot / event。
- 前端不得用卡牌位置推断征服、据守、得分、控制权变化或战斗结果。

## 自动检查范围

`check:tabletop-layout` 至少检查：

- 双方都有完整七个玩家区域。
- 中央战场数量为 2。
- 符文牌堆大小为 12。
- 所有区域在容器范围内。
- 关键区域顺序符合桌垫语义：本方传奇/英雄在左、基地在右、符文在手牌左；对手基地在左、传奇/英雄在右。
- 明显重叠的关键区域会失败，避免桌垫条框和组件约束框再次错位。

视觉还原度仍需要 Playwright appshot / visual diff 复核；本契约负责守住规则区域不会漂移。
