## 迭代一 统一费用计算与原生费用预览

目标是让提示、预览和实际扣费使用同一份费用计算逻辑。选中急速、改变目标或支付特性后，玩家应在确认前看清总费用、将使用的资源及不足原因。

| 工作 | 实施内容 | 验收条件 |
|---|---|---|
| 共享费用计算 | 从现有出牌计划中抽出无副作用的费用计算；保留已验证的支付授权和提交逻辑 | 同一状态和选择产生一致的预览、授权与扣费结果 |
| 费用顺序 | 按 356 区分基础费用调整、强制及可选额外费用、增费、减费和最终总额调整 | 无视基础费用仍保留适用的额外费用；无视法力仍保留符能；无视一切费用使用不同语义；减费不产生负值；可选额外费用减至零后仍保留相应已支付标志 |
| 权威预览协议 | 使用带类型的请求与响应，关联身份、房间、prompt、tick 和本次选择；返回费用明细、可支付状态、分项缺口及原因 | 请求不改变池、物体、随机状态或日志序列；客户端提交的费用数值不能授权支付 |
| 原生支付面板 | 卡面与费用摘要固定，目标、额外费用和资源区可滚动；选择变化后更新后端预览，展示法力和各特性符能的合计 | 旧响应不覆盖新选择；当前预览未就绪或后端判定不可支付时不能确认；失败继续保留输入 |

建议新增 `PlayCostPlan` 和 `PlayCostQuoteDto` 等带类型模型，名称可随实现调整。正式提交必须依据当前权威状态重新校验，预览结果不充当可复用的支付许可。将报价所需计算逐步移出 `MatchSession` 的重复分支，限定在本批涉及的路径内重构。

本步处理当前卡池已实现费用族和后三张代表牌所需的覆盖、减免语义。尚未实现的费用替换和新卡机制继续留在规则台账中。精确指定池中优先消耗哪一种彩虹或彩色资源可另立任务；本步至少准确展示服务器计划消耗的资源。

## 迭代二 修正常驻牌确认和入场时机

将常驻牌与法术在确认后的路径分开。这个步骤调整到效果再次打出之前，因为两类打出必须共用正确的实体确认流程。

- 普通单位与非单位装备完成合法性和支付后，按各自规则离开待处理结算链并成为场上物体；正常单位休眠、已支付急速或明确例外仍使用 `PrepareUnitEntry`。
- 法术继续使用合法的响应与结算链流程。常驻牌自身落场与其产生的触发技能分开处理，按规则收集触发并进入相应确认流程；不能因实体立即落场而丢失触发或额外添加一次触发。
- 原生桌面在权威快照到达后显示入场卡牌，提供简短的费用支付和入场反馈；存在后续触发或选择时显示当前处理内容和行动者。
- 旧测试中用于等待普通单位落场的让过优先权命令逐项迁移。每项记录规则依据，保留费用、控制者、区域、触发顺序和回放断言。

本步完成条件：无触发的普通单位和装备不会额外要求双方让过优先权；有触发的单位仍产生正确的后续任务；法术响应、迅捷与反应权限、战斗时机相邻回归通过。新旧行为差异须先由针对性失败用例复现，再修正实现。

## 迭代三 效果再次打出及后续选择

为效果授予的再次打出建立服务器内部上下文，复用前两步的费用与确认逻辑。上下文记录实际执行者、来源区域及物体世代、允许的目的地、费用调整、是否可放弃和父效果的继续位置。客户端只能选择服务器提供的候选，不能自行声明免费、从任意区域打出或指定执行者。

先明确每个效果的目标锁定、执行中选择、生成待确认项目和继续确认的时点。依据 355.10.a 与 355.17，手牌中的选择不能一律作为父法术的公开目标；公开废牌堆与场上目标则按其目标规则处理。按 330.2、359.3.b 和相关 FAQ 接入现有结算链，避免把所有再次打出简单实现为递归调用普通出牌。

首批限定以下三个效果族，并检查复用同类入口的相邻卡牌：

| 代表牌 | 需要实现的行为 | 必须包含的反例或边界 |
|---|---|---|
| 蚀魂夜 OGN·198/298 | 从自己的废牌堆再次打出单位，只覆盖其基础法力，继续计算应付符能和适用额外费用；目的地遵守该次打出的合法权限 | 符能不足、错误来源、非单位、费用与入场选项、来源改变后的过期选择 |
| 前来相助 SFD·111/221 | 在效果执行时选择是否打出手牌单位，到当时受控的合法战场，施加 3 法力减免 | 四费单位补付剩余 1 法力且继续支付符能；主动放弃；无受控战场；禁止打出时的处理；对手看不到未公开的手牌候选 |
| 传送门大营救 OGN·102/298 | 放逐后由原拥有者打出到其基地，覆盖基础费用，重新处理适用额外费用、物体身份和入场触发 | 所有者与控制者不同；旧伤害和贴附清理；无视基础费用仍有额外费用；无法再次打出时已执行步骤如何保留 |

只有卡面或规则明确允许放弃时才提供“放弃”操作。Escape 可以关闭未提交的编辑面板；已进入必须处理的服务器选择时，应能重新打开并继续，不能靠关闭窗口跳过规则任务。

再次打出可能在父效果执行中等待玩家选择。等待期间必须保存继续位置，断线或服务端恢复后重建同一合法选择；重复提交不得重复扣费或再次落场。嵌套命令被拒绝时保持该步提交前状态不变，但不能回滚已经成功执行的父效果及其已付费用。是否跳过无法执行的指示，按对应卡面、358.3.a 和相关 FAQ 判断。

原生界面沿用出牌面板和公共牌堆浏览：展示“由哪张牌产生的选择”、当前可选卡图、合法目的地和权威费用，完成后自动回到正在执行的效果。其他玩家只收到其有权查看的等待信息和公开事件。

## 原生视觉与交互验收

继续使用现有深色牌桌、官方卡图和统一按钮样式。每个小迭代都做对应窗口的实际检查，重点是费用易读、操作层次明确、选择后有反馈。

- 费用明细区区分卡面费用、调整项和最终应付；关键确认按钮固定在可见区域，金额和特性同时使用文字与视觉标记。
- 复杂效果先呈现当前步骤，完成后再进入下一步；卡牌、目标与资源较多时可滚动浏览，保持已选项目可识别。
- 覆盖 1280×720、1440×900、1920×1080，长中文文本、长手牌与满场场景；检查键盘导航、取消、拒绝反馈和断线恢复。
- 动画跟随服务器事件，不能以动画结束决定规则推进；提供减少动画的设置，避免过场遮住必须响应的选择。
- macOS 使用最终导出包在源码目录外检查。Windows 在实际环境检查启动、中文字体、输入、100% 至 200% 缩放、双端联机和恢复，并保存独立证据。

## 交付顺序和外部依赖

执行顺序为共享费用与预览、常驻牌确认时机、三个效果族及其原生选择，最后进行完整对局和包验收。每步单独提交，说明修复的规则、迁移的测试和尚未覆盖的边界。

实施主要涉及 `CoreRuleEngine`、`PaymentCostRules`、`MatchSession`、卡牌行为注册、Contracts、状态保存与恢复，以及 Godot 的 `PlayCardOverlay` 和相关提示控制。新增状态必须同步考虑协议投影、序列化、日志和旧存档兼容，不能只修改即时对局内存。

GitHub 推送权限和 Windows 执行环境分别记录为外部依赖，不阻止本地规则与 macOS 迭代。只有权限具备后才能上传工作流并记录远端 CI；只有 Windows 实机证据具备后才能标记 Windows 验收通过。

本批结束时应交付规则与交互变更、对应规则证据、测试迁移说明、最终原生截图、双平台包及校验值、已知问题清单。新增全卡池机制、完整赛事系统和正式发行签名继续独立排期；本批通过后仍不据此宣告所有规则和卡牌已实现。
