# ADR 0005：共享多局比赛状态与先后手

依据中国区官方[《赛事规则》](https://cdn.playloltcg.com/lol/2026/10/2026-10-10/0d5c26b5535345d48e1afafb3e2a0018.pdf) 404.1–404.3、407.1–407.4，比赛层和核心单局分开。`MatchSeries` 是共享的不可变流程，记录单局历史，从历史派生胜局数、当前局号、指定玩家和阶段；`bestOf` 只接受 1、3，分别需要 1、2 个胜局。平局不加胜局，因此三局两胜可以超过三场实际对局。未达到胜局要求时继续比赛，不实现时限或 408 超时流程。

创建时由服务器既有的私有开局种子通过独立的 `match-series-play-order-v1` SHA-256 流确定首局指定玩家。该玩家选择自己先手或后手，然后进入暗提交阶段；调用方须在双方卡组通过准入、战场同时公开后，调用 `StartGame` 进入核心 110。上一局败方选择下一局先后手；平局直接沿用原顺序并进入提交阶段。局间先后手与战场公开的先后次序仍按现开赛 ADR／BACKLOG 的“待确认”约定。

`MatchSeriesState` 是内部持久化数据，保留两名玩家的固定顺序、初始指定玩家和逐局状态；集合防御性复制且只读。`Restore` 使用日志中的原始开局种子核对首局指定玩家，并拒绝非法玩家、局号、阶段、平局后变更顺序、达到胜局后继续对局和提前终局。同一局结果重复结算幂等，冲突结果拒绝。恢复过程不重新抽签，不把外部当前默认配置作为历史输入。

`RoomMatchSeries` 在第二名玩家的入座事务里创建比赛，`SeriesState` 进入权威帧和状态哈希，玩家与观战快照仅投影公开比赛进度。选择命令沿用 `SubmitIntent`／`SubmitAsync` 的原始输入校验、行动窗口、幂等缓存、日志提交与动作重放；精确线上形状见 ADR 0001。未选择顺序不能提交现开卡组或准备；双方准备后，核心 110 使用已选择的顺序，构筑继续使用原来的随机先手流程。

核心单局结束后，比赛层记录结果；未达到胜局要求时通过 `MatchState.Create` 清空所有游戏内字段，保留房间身份、原始私有种子、随机游标、卡池与比赛账本，再进入下一局选择／提交阶段。私有 `LastCompletedSeriesGame` 保存刚结束一局的完整核心终局帧，剥离比赛包装字段避免递归；它随权威日志持久化并校验，不进入玩家或观战快照。公开事件引用使用该终局上下文投影，避免清空新局状态后丢失隐藏对象标记。下一局开局后的事件使用新局上下文。单局的 `MATCH_WON` 转成 `GAME_WON`，比赛最后一局才保留 `MATCH_WON`；大厅战绩入口也校验比赛确已结束。现开战绩的 `score` 为胜局数，复用既有持久化字段；构筑战绩分数含义不变。每局完整动作及终局帧仍在同一房间日志里，局间帧、令牌重连、各次提交和先后手选择都由相同恢复／重放流程核对，不重新生成卡池。

现开私有 `SealedBattlefieldHistory` 在双方准备后的开局事务中保存每局初始战场选择、局号及是否平局复用。它保留在比赛包装帧中，单局核心终局帧剥离此字段；公开 `series.usedBattlefields` 只派生已展示且实际占用实体的记录。正常换局按印次数量检查剩余实体；平局锁定上一局配置和原战场，不再次消耗副本，单局制也不重新随机抽选。提交与准备都检查这些限制，恢复时核对开局记录、复用关系及实体用量。

共享模型 `AwardGameLoss` 允许可信比赛层在核心开局前后结算判负；`MatchSeriesGameState.skipped` 只表示尚未进入核心开局就被判负，必须有胜者，不能伪装成平局或已开局。服务端接口与日志／恢复见 ADR 0001。局间账本按真实局号关联已开局记录，跳过局没有战场记录。首局完全跳过后的下一局保留初始主配置，已展示战场后的判负保留实体消耗；牌池、先后手指定、胜局、小分和比赛结束继续沿用共享流程。

可信应用层通过 `MatchTournamentAdjudicationService` 执行判负，并在最终胜局后保存整场战绩；它与现开 Hub 共用按最终比赛账本补写战绩的入口及小分生成函数。底层状态判负只用于该服务及无外部副作用的动作重放。日志提交失败不写战绩；战绩写入失败可在原判负或玩家命令的幂等重试时补写，冷恢复后的空事件回执同样检查最终比赛账本。已保存的相同战绩保留原时间和单条记录，冲突数据拒绝覆盖。

终局补写调用共享 `IMatchResultStore.RecordFinalMatchResultAsync`，把首次保存、重复确认和冲突检查作为一个原子操作。内存存储通过 `GetOrAdd` 保留第一份记录；PostgreSQL 在同一事务中锁定 `matches` 父行，再读取战绩及玩家小分，缺失才写入，支持独立存储实例及并发 API 请求。相同结果不会更新原完成时间或重写玩家记录，冲突结果拒绝覆盖并回滚；注入的其他存储默认使用按存储实例共享的异步锁。现开 Hub 与可信判负共用此入口，构筑赛原 `RecordMatchResultAsync` 写入行为保留。

公开现开建房已连接真实房间配置和目录，支持前端按 ADR 0001 联调。当前房间回归使用真实卡池，以主动投降、可信判负或测试终局适配器提供平局，验证比赛生命周期、局间约束与恢复，不代替 BACKLOG 的完整打牌终局和 L2 验收。
